## Problem Statement

平台管理员需要统一查询 OpenBot 服务端运行日志和业务审计日志，避免在多个入口之间切换。Agent 已有 Opik 观测能力，统一日志查询不应重复建设 Agent 轨迹平台，也不应改变 Activity 页面或 PostgreSQL 审计记录的权威性。

## Solution

自托管 OpenObserve，作为仅平台管理员使用的服务端运行日志和审计副本查询入口。保留 Opik 查询 Agent 执行轨迹与模型调用；适用时以 Run ID 关联同一次运行。保留 Activity 和 PostgreSQL 审计记录。仅收集接入后的必要字段，不上传正文或凭据。运行日志保留 30 天，审计副本保留 90 天；日志平台故障不阻断业务。

## User Stories

1. As a 平台管理员, I want 在 OpenObserve 查询服务端运行日志, so that 我能使用统一入口排查服务问题。
2. As a 平台管理员, I want 在同一平台查询审计事件副本, so that 我能结合操作记录理解故障背景。
3. As a 平台管理员, I want 按时间、服务、环境和级别查找日志, so that 我能缩小排查范围。
4. As a 平台管理员, I want 查看经过脱敏的错误信息, so that 我能定位问题而不接触不必要的敏感数据。
5. As a 平台管理员, I want 使用请求 ID 关联适用的日志, so that 我能追踪同一次请求。
6. As a 平台管理员, I want 使用 Run ID 关联日志和 Opik 中同一次运行, so that 我能继续分析 Agent 执行过程。
7. As a 平台管理员, I want 无关联 Run 的系统日志仍可查询, so that 启动和基础服务故障也能排查。
8. As a 平台管理员, I want 保留 Opik, so that 已有 Agent 观测能力继续可用。
9. As a 获授权的业务用户, I want 继续使用 Activity, so that 我无需进入运维平台查看业务审计记录。
10. As a 平台维护者, I want PostgreSQL 继续保存权威审计记录, so that 日志副本缺失或过期不影响业务记录。
11. As a 平台维护者, I want 自托管 OpenObserve, so that 平台自行管理日志环境与数据。
12. As a 平台管理员, I want 运行日志保留 30 天, so that 我能查询近期故障且限制存储增长。
13. As a 平台管理员, I want 审计副本保留 90 天, so that 我能查询更长时间范围的操作背景。
14. As a 平台维护者, I want 只有平台管理员能够访问 OpenObserve, so that 普通用户不能读取集中日志。
15. As a 用户, I want 日志上传前去除凭据且不采集正文, so that 排障不造成额外内容暴露。
16. As a 用户, I want OpenObserve 故障时业务仍可运行, so that 观测服务故障不会阻断工作。
17. As a 平台维护者, I want 缓存和重试有上限, so that 日志导出不会无限消耗资源。
18. As a 平台维护者, I want OpenObserve 恢复后继续接收新日志, so that 无需回灌即可恢复日常观测。
19. As a 平台管理员, I want 历史审计继续通过 Activity 查询, so that 不回灌历史数据仍保留原有查询能力。

## Implementation Decisions

- 已确认采用自托管 OpenObserve，首期覆盖服务端运行日志和审计日志，不自动上传桌面端或 CLI 日志。
- 保留 Opik、Activity 和 PostgreSQL 审计存储。集中日志是查询副本，不替代业务审计或积分账本。遵守 ADR 0004 关于模型网关默认不记录请求与响应正文的约束，沿用 ADR 0006 的职责划分。
- 复用已有审计 OTLP HTTP 导出接口；文档定义日志专用 endpoint 优先于通用 endpoint，并支持 headers、service.name 和关闭导出。实际镜像行为及 OpenObserve 接收兼容性需要实施验证，不能仅凭文档判定已接通。
- 修改范围为自托管部署、服务端日志采集与导出配置、上传前字段过滤、访问控制、保留策略和运维说明。服务运行日志来源需按实际部署验证，不假设现有审计导出已覆盖运行日志。
- 分开管理运行日志与审计副本的保留策略，分别为 30 天和 90 天；不改变 PostgreSQL 审计保留规则。
- 必要字段包括时间、服务、环境、级别、错误信息和适用的请求 ID、Run ID。无关联 Run 的日志不伪造 Run ID。关联要求是能够定位同一次运行，不要求首期建设自动跳转 UI。
- 上传前去除凭据，不采集对话正文、模型输入输出、工具参数或工具返回正文。错误信息和嵌套字段同样受此限制，不能通过异常文本绕过过滤。
- OpenObserve 仅允许平台管理员访问，覆盖查询 UI 和查询 API；服务端写入使用受控凭据，不向普通用户暴露。
- OpenObserve 不可用时采用有限缓存和重试，超过限额允许丢弃副本，业务请求与 PostgreSQL 审计写入不受影响。不承诺完整无损、恰好一次投递或故障期间副本全部补齐。
- 从接入时开始收集新日志，不回灌历史数据。
- 具体版本、采集组件、缓存容量、重试次数及部署资源由实施时验证并记录；它们不是已确认的产品选型或容量承诺。

## Testing Decisions

- 用户已确认端到端验收边界：从实际服务操作产生错误或审计事件，经采集导出，到 OpenObserve 查询结果。优先以这一最高层集成边界验证，不测试内部函数调用顺序或配置文本是否恰好匹配实现。
- 在隔离的自托管测试部署中产生可识别的新服务错误及审计事件，验证能够查询，必要字段正确；验证同一审计事件仍能通过现有 Activity/API 查询且保存在 PostgreSQL。
- 运行一次带 Run ID 的 Bot 执行，验证日志与 Opik 可以定位到同一次 Run；同时验证无 Run ID 的系统日志正常入库。
- 使用管理员、普通用户和未认证请求验证 UI/API 访问边界。
- 使用合成凭据、对话正文、模型正文和工具正文作为敏感测试标记，检查实际发送载荷及最终查询结果均未泄露；包含错误信息与嵌套字段场景。
- 停止 OpenObserve，持续产生业务请求与审计事件，确认业务成功且审计记录仍持久化；达到配置的缓存/重试上限后确认资源有界，允许丢弃。恢复后验证新日志继续入库，不要求丢弃数据补齐。
- 在隔离环境使用可控时间或缩短等价策略周期，验证两类数据独立过期，并检查生产配置对应 30/90 天；不能只看配置值就声称清理行为通过。
- 验证正常接入不会导入历史记录，Activity 历史查询不回归。
- 现有先例包括 Bun 的 Compose 部署配置测试，以及审计 OpenAPI 的筛选与导出契约测试；保留这些回归检查。它们不能替代真实接收、权限、脱敏、过期和故障恢复测试。尚未发现可直接复用的 OpenObserve 端到端测试，需要补充上述统一集成测试入口。

## Out of Scope

- 替换 Opik，或将 Agent 详细轨迹、模型输入输出搬入 OpenObserve。
- 删除或改造 Activity 为日志平台入口，替换 PostgreSQL 权威审计记录或积分账本。
- 桌面端与 CLI 本地日志自动上传。
- 历史运行日志和历史审计数据回灌。
- 告警规则、定制仪表盘、面向普通用户的集中日志查询。
- 无损导出、无限缓存、故障期间日志必定补齐的承诺。

## Further Notes

本规格综合本轮已确认的分项决策与验收标准；发布规格不表示接入已经实现或验收通过。当前仓库服务端主要由发布镜像交付，完整后端源码不在仓库，审计导出行为目前主要依据文档与 API 契约。实施时必须验证镜像真实行为；若必要的字段过滤、Run 关联或非阻塞导出无法通过现有接口满足，需要明确列出上游修改依赖，不得以部署配置测试代替功能完成。
