## What to build

通过已有审计 OTLP HTTP 导出链路，将新业务审计事件汇入 OpenObserve；同一操作仍可在 Activity 查询并保存在 PostgreSQL。

沿用父规格及 ADR 0006：保留 Opik、Activity 和 PostgreSQL 审计权威记录；仅平台管理员查询，不上传凭据或正文。告警、定制仪表盘及桌面/CLI 自动采集不在范围内。

## Acceptance criteria

- [ ] 在实际部署镜像上执行可识别的业务操作，验证审计事件经真实导出链路进入 OpenObserve，不能用人工构造 OTLP 事件替代主验收。
- [ ] 同一操作的审计记录在 PostgreSQL 持久化，并可通过 Activity 及其现有 API 查询；原有筛选与导出行为不回归。
- [ ] 复用日志 endpoint、通用 endpoint、headers、service.name 与关闭导出的现有配置契约，验证实际使用的 endpoint 优先级及认证兼容性。
- [ ] 审计副本与运行日志可区分并独立配置保留策略；保留必要的事件信息及适用的关联 ID，沿用现有审计 surface 语义。
- [ ] 在审计上传边界同样过滤凭据与正文；合成敏感标记覆盖嵌套字段和错误文本，验证实际发送载荷与入库内容均不泄露。
- [ ] 审计数据仅供平台管理员从 OpenObserve 查询；普通用户继续遵循 Activity 原有权限。
- [ ] 新接入不回灌 PostgreSQL 历史审计数据；接入前记录仍可从 Activity 查询，接入后事件可从两处查询。
- [ ] 关闭导出或 OpenObserve 不可用时，业务操作及 PostgreSQL 审计写入继续成功；不承诺导出副本无损。
- [ ] 提供端到端可重复验证及证据，覆盖实际业务操作、审计副本查询与原有查询；若镜像无法满足契约，记录并解决上游依赖后才能完成。

## Blocking rationale

依赖任务 1（接入当前业务系统运行日志，统一到 OpenObserve 查询）提供已验证的运行日志端到端部署与查询链路。
