Part of #61

Blocked by: #68, #69, #70, #71

## What to build

将微信支付宝收退款账单与本地订单核对，提供可审计的异常处理。

## 实施边界与当前状态

可使用脱敏官方账单夹具独立实现，不等待真实商户联调完成；真实下载权限由T11验证。

## 阻塞关与解除条件

依赖两适配器与退款状态机。夹具测试可完成本票，但上线要求T11实际账单另行通过。

只有上述前置任务验收完成后才进入本票正式实施；可以提前阅读和准备夹具，但不能用提前准备关闭本票。

## Acceptance criteria

- [ ] 分别导入/下载两渠道交易与退款账单，保留来源日期、完整性校验和导入批次，重复导入不重复造差异。
- [ ] 按渠道交易、订单、退款标识及金额币种核对，区分未履约成功收款、重复收款、少/多款、退款未知和渠道手续费，不混作积分消费。
- [ ] 漏通知但已可信核实的成功付款可幂等触发原订单履约，其他金额不符等进入人工调查，不覆盖余额或追扣。
- [ ] 运营者可查询、认领、记录证据/原因并通过受控命令处理差异；不得直接编辑历史流水，普通用户不能访问他人差异。
- [ ] 每日计划可重跑，下载失败/账单未就绪保留待处理状态，服务重启不丢处理进度。
- [ ] 用双渠道成功/退款/重复/缺失/币种金额错误样例和多次重跑验证差异数量及最终订单结果；真实交易证据接入不改变解析规则。
- [ ] 形成可观察待对账与异常积压指标，不在日志或导出中暴露渠道凭据或不必要个人数据。

## 测试边界与完成要求

遵循父规格 #61 与 ADR 0003/0004，保持 Lago 社区版、OpenBot 北京时间周期及唯一积分账本。优先从受信业务 API/用户行为验证，使用真实 PostgreSQL/Lago；支付协议票在外部适配器边界使用替身，真实商户结果由专门闭环票验证。参考模型或静态调研不能替代本票要求的生产模块/集成证据。

完成时附可重复命令或操作步骤、版本、期望/实际结果、故障场景和未验证范围；不得包含凭据。`ready-for-agent` 仅表示任务已说明清楚，不表示依赖或外部条件已解除。
