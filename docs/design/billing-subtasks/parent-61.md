## Problem Statement

OpenBot 个人用户需要通过微信或支付宝购买月付套餐和消费积分，清楚知道余额、预留、实际消费和退款状态。平台需要让所有使用付费资源的执行遵守同一余额与消费上限，包括对话、后台工作、辅助模型调用、Task、Delegation 和 Subagent；并发、失败、重复通知、周期切换和迟到用量都不能造成透支、重复扣费或错误欠款。

当前已有客户端、API 合同、可编辑的外部 Harness 和预构建后端镜像，但尚未取得与运行镜像匹配的可构建后端及生产积分账本。仅添加收银台、前端余额检查或事后用量汇总无法提供可靠付费服务。

## Solution

提供个人独立 Billing Account、月付 Subscription Plan 和长期有效的 Credit Pack。用户主动通过微信支付或支付宝购买，服务端核实到账后发放权益；收费步骤先预留 Credit，再按实际资源消耗结算，余额不足时暂停新增消费。用户可以查看订单、可用与预留积分、消费明细、原周期调整和退款进度。

OpenBot 管理实时积分账本、北京时间周期、人民币收退款及用户账单。自托管 Lago 社区版保持 UTC，仅以零金额计量汇总资源用量和整数微积分；两者按原始事件对账，Lago 不二次扣费。平台模型调用与既有 Bifrost 规格共享同一账本和可信执行边界。

## User Stories

1. As an OpenBot 个人用户, I want 独立拥有 Billing Account, so that 我的订阅、积分和消费不与其他用户混合。
2. As an 用户, I want 用微信支付购买套餐, so that 能使用熟悉的支付方式获得服务。
3. As an 用户, I want 用支付宝购买套餐, so that 可以选择适合自己的支付渠道。
4. As an 用户, I want 购买按月生效的 Subscription Plan, so that 持续获得周期积分和资源额度。
5. As an 用户, I want 单独购买 Credit Pack, so that 当期积分不足时可以补充。
6. As an 从未订阅的用户, I want 直接购买积分包, so that 可以使用基础按量服务。
7. As an 订阅已过期的用户, I want 继续购买和消费积分包, so that 已购买积分不会因未续费而无法使用。
8. As an 用户, I want 在统一网页收银台购买、续费和充值, so that 不必理解不同客户端的支付实现。
9. As an 桌面用户, I want 打开网页并扫码付款, so that 能从桌面客户端完成购买。
10. As an 手机用户, I want 在渠道支持的浏览器中付款并返回订单页, so that 可以确认购买结果。
11. As an 用户, I want 付款尚未核实时显示支付确认中, so that 不会把页面跳转误认为到账。
12. As an 用户, I want 同笔付款只发放一次权益, so that 重复通知不会扰乱余额和订阅。
13. As an 用户, I want 漏通知的成功付款能通过查单补发权益, so that 不会付费却长期无法使用。
14. As an 用户, I want 服务端确认并实际开通时才起算首次周期, so that 支付确认延迟不会侵占权益时间。
15. As an 用户, I want 提前续费接在当前周期后, so that 不损失已购买的剩余时间。
16. As an 用户, I want 下一周期开始时才收到下一期套餐积分, so that 续费不会提前改变当前额度。
17. As an 用户, I want 过期后重购从新的开通时间起算, so that 不为中间未使用的时间付费。
18. As an 月末开通用户, I want 短月份取月末后恢复原购买日, so that 二月不会永久改变续期锚点。
19. As an 用户, I want 明确知道套餐积分当期有效, so that 能安排周期内的消费。
20. As an 用户, I want 额外购买的积分长期有效, so that 不必为短期内用不完而担心。
21. As an 用户, I want 优先消耗即将到期的积分, so that 尽量减少未用积分失效。
22. As an 用户, I want 功能权益和积分余额分别显示, so that 积分用完不会被误解为订阅失效。
23. As an 基础用户, I want 使用对话、Routine、Goal 和 Check-in, so that 不订阅也可按量使用基础服务。
24. As an 订阅用户, I want 获得更多周期积分、并发和自动任务名额, so that 套餐价值明确。
25. As an 订阅到期用户, I want 保留数据和任务配置并选择基础额度内启用的任务, so that 降级不会删除工作。
26. As an 用户, I want 套餐变更下周期生效, so that 当期权益和积分规则保持稳定。
27. As an 已预购用户, I want 先完成原续费退款再购买新档位, so that 同一周期不会存在两份套餐承诺。

30. As an 用户, I want 每个步骤开始前锁定单价, so that 调价不会追溯改变已开始的步骤。
31. As an 用户, I want 每次收费步骤先预留积分, so that 并发工作不会重复使用同一余额。
32. As an 用户, I want 步骤完成后按实际消耗扣分并释放余量, so that 未使用额度及时恢复。

## Implementation Decisions

### 权威与依赖边界

- 遵循 ADR 0003、0004：OpenBot 是唯一实时积分权威，Bifrost 管理平台模型出口，Lago 社区版负责零金额用量汇总。Lago 钱包余额、Bifrost 预算均不能替代 OpenBot 账本。
- 个人 Billing Account 通过服务端稳定身份和 Personal Workspace 关系解析，不使用可变邮箱、客户端自报付款人或部署行为者作为扣费授权。身份停用及后台执行约束与 Casdoor 规格一致。
- 每个消费账户建立持续 Metering Relationship，与月付 Billing Subscription 区分；套餐过期不会终止积分包的计量关系。
- 当前仓库可以新增独立账务模块、支付适配器、Lago 同步 worker、API 合同、页面与隔离测试。可编辑的外部 LangGraph Harness 只能覆盖其自身，不能证明内建 Bot 和全部后台路径已经强制计费。
- 已定位移除后端前的历史基线 `6d1919a3b53a0730894258f197f3beb4e8db4f2f`，以及后台准入、通用 runner、模型配置、Run 签名、工具 callback 和委派候选点。历史代码不等于当前运行镜像源码；必须取得匹配构建或隔离验证完整历史分支，不能直接恢复一个旧目录就上线。
- 账务模块建议沿用已发现的 Bun/TypeScript、Drizzle、PostgreSQL 路线。嵌入后端还是独立部署由可信后端能力验证决定；不因此更改账本业务权威。技术接口须先定义合同，不能把拟新增 reserve/settle 操作写成已存在能力。

### 商品、周期与积分

- 首期月付套餐加积分包，微信支付宝主动付款，不自动扣款。基础用户可使用对话和自动工作；订阅主要增加周期积分、并发及自动任务名额。
- 套餐积分仅当期有效、不结转；积分包长期有效；优先扣即将到期积分。到期保留数据和配置，超基础额度的任务暂停，由用户选择启用。
- 首次及过期重购从服务端确认并实际开通时起算；提前续费接续当前周期，仅在下一周期开始发积分。最多预购一期；中途换档下一周期生效，已预购换档先完成退款再买，退款中禁止重复购买该周期。
- 周期按 Asia/Shanghai 的原始购买日和时间计算，短月份截至月末，随后恢复原日号，不能连续从截短日加月。周期使用含起点、不含终点的区间，转换为 UTC 瞬时保存；过期重购产生新锚点。
- 资源按实际用量计价，分别配置模型输入、输出、缓存 token 和工具次数/时长价格；步骤预留时锁价。积分六位小数，内部整数微积分，1 积分等于 1,000,000 微积分；每个步骤汇总后四舍五入，不对每个 token 或流式片段取整。人民币使用整数分，禁止浮点计费。
- 正式价格、积分数量、资源额度及默认 Run 上限另行配置并版本化；演示数字不是正式价格，生产配置缺失时禁止销售。

### 生产账本与执行

- 持久化账户、积分批次、价格版本、预留与批次分配、消费流水、Run 上限、调整记录、接口幂等记录及待发送记录。余额变化、流水与待发送记录在同一数据库事务内提交，外部网络调用不持有该事务。
- 每个收费步骤先确认账户状态、可信付款归属、原始 Run 剩余上限和可用批次，原子预留，再执行。并发任务不能重复使用余额，账户与 Run 使用一致锁顺序；数据库约束保证非负可用额、批次守恒及唯一结算。
- 主动工作由发起人支付，Routine、Goal、Check-in 由创建者的已授权账户支付，Delegation 和 Subagent 继承原付款人及上限。外部事件无授权付款人不执行；转移、分享、编辑任务不隐式改变付费账户。
- 一次 Run 固定消费上限，提高需要用户明确确认；子代理和委派共享上限。模型和工具调用都受约束，无法限制单步最大成本的路径暂不开放。
- 平台模型遵循既有 Bifrost 规格：每次请求通过可信服务端验证有效预留，Harness 不持有平台供应商密钥，不允许绕过网关。辅助模型调用同样有可信费用记录，现有运行遥测不是完整计费来源。
- 首期关闭 SDK 和网关自动重试与自动故障切换。用户明确重试产生新的实际调用和预留；同一调用的结算重投保持原身份。不能将流式片段重复累计为实际用量。
- 用户取消或未达目标仍结算已发生的有效消耗；平台故障导致的无效消耗和重复执行由平台承担。无法确认用量时最多预留 24 小时，之后释放，迟到成本归平台，不追扣；可能已执行的调用不自动重发。
- 跨周期已开始步骤沿用原预留批次，剩余过期额度直接失效，后续步骤只能使用有效额度。记录发生时间、结算时间和来源批次周期三个维度，不能从 Lago 事件时间反推扣减批次。
- 因余额不足暂停的工作需用户明确恢复，周期性安排只执行未来计划，不补跑历史次数。订阅降级允许已开始步骤结束，后续执行遵守基础资源额度。
- 本地账本不可可靠预留或保存记录时停止新增消费；Lago 不可用但本地账本和待同步记录可靠时可继续，恢复后补传。已开始步骤保留实际用量待结算。
- 同一结算身份同内容重试返回既有结果，不同内容拒绝。调整以账户、原事件及调整类型为唯一作用域，周期和金额不可变；合法更正追加独立有来源事件，不覆盖原记录。

### 支付、权益与退款

- 自有商户号直连微信支付和支付宝，统一网页收银台，人民币收款。订单保存商品与价格快照、账户、金额币种及 30 分钟到期时间，渠道尝试与业务订单区分。
- 微信采用经官方文档核实的 Native/H5、查单、关单、退款、查退款、通知及交易账单能力；支付宝采用电脑/手机网站支付、查单、关单、退款、查退款和账单下载能力。固定 SDK 与协议版本，不混用弃用 SDK 示例和未核验的 REST 路径。
- 微信 H5 仅适用于已支持的外部手机浏览器；内置或嵌入浏览器需明确引导至支持环境。需要 JSAPI 时另行核验产品与接入，不假定统一网页自然覆盖全部场景。支付链接有效期与订单有效期分开管理，刷新链接不延长订单。
- 通知先验签解密并校验商户、应用、订单、金额和币种，再确认付款；用户回跳不作为到账证据。渠道查单补偿通知遗漏，已核实的同笔付款只履约一次，权益发放可在崩溃后可靠恢复。
- 一个业务订单可存在多次支付尝试，但只能履约一次。重复收款或两渠道同时成功进入异常退款，不能重复发积分。
- 到期先查单并关单；迟到通知若真实支付发生在有效期内仍履约，失效后真实付款进入异常退款。关单与付款竞争必须以核实的渠道结果处理。
- 首期人工审核退款：未使用积分包及未开始续费周期可申请全额退款；已消费积分包、已开始订阅不提供常规自助退款，平台故障和重复收款单独处理。
- 审核退款时冻结对应额度或待生效权益。渠道确认成功后撤销，确认终止且未退款才解除冻结；未知或处理中继续冻结并查询，超过 24 小时转人工。解冻仍遵守原积分有效期。退款重试使用原渠道退款标识，受理成功不等于完成。
- 平台补偿恢复原扣减来源；来源套餐积分已过期时，发放到账后 30 天有效的 Compensation Credit，并关联原消费。
- 商户密钥、公钥/证书、产品权限及 HTTPS 回调由部署和商户配置承接，不进入前端、仓库或规格正文。真实支付验收须有实际产品开通与渠道联调证据。

### Lago 同步、对账与用户界面

- 每个计费账户建立独立计量关系，以零固定费、零用量单价汇总资源数量与实际扣减微积分，不把积分消耗变成新的人民币应收，也不要求 Lago 独立复算每步积分价格。
- 资源用量和积分结算分别上报并关联步骤 ID；区分用户承担、平台承担和用户自付。自付模型不收模型 token 积分，实际使用的平台收费资源仍收费；此规则不新增 BYOK 接入能力，现有订阅登录路径不迁移。
- 事件上报保存原始时间与稳定身份，重试不改变时间或 ID。原始整数微秒作为 occurrence_us 同步，API timestamp 从同一整数生成精确十进制秒字符串；禁止隐式浮点转换。
- Lago 查询两端包含且返回 timestamp 仅毫秒精度。按稍扩大的 UTC 窗口粗筛，再以经本地原记录校验的 occurrence_us 执行精确半开过滤。缺失或冲突时间进入差异清单，不静默降为毫秒判断。
- 固定本地持久化发送水位及预期事件集合，读取全部分页，重扫并按稳定 ID 去重，核对内容与同步状态；总数或总额两次相等不能证明完成。当前水位之外的事件留下一轮，历史迟到事件可重新打开原周期核对。
- 已出账窗口保留历史快照，以“原快照加确认调整”展示迟到差异，不要求 Lago 自动改写旧账单。追加调整幂等，不重复扣积分。
- 每日分别核对渠道人民币收退款与订单、本地积分流水与 Lago 微积分、原始资源用量与费用承担方。差异先调查，不覆盖余额、不自动追扣，所有处理保留原因。
- Lago 只保存账户/步骤标识、资源类型、用量、归属和时间等必要信息，不保存对话、提示词、模型输出或支付密钥。
- 用户账单以 OpenBot 为准，展示可用、预留、结算确认中、退款处理中、补偿和原周期调整；Lago 原始账单仅供运营核算。沿用既有组织作用域、问题详情错误、写入幂等键和分页合同，由源合同生成客户端。
- 公共购买和查询 API 经服务端映射个人账户；预留、结算等内部操作仅对可信服务开放。渠道回调以订单和验签解析归属，不能信任客户端或回调 URL 指定付款人。
- 回滚停止新增购买和消费，但保留已收支付通知、查单、退款、在途结算及对账处理，不清空或回滚历史流水。

## Testing Decisions

- 用户已明确确认主测试边界：从受信服务端业务 API 发起购买、消费、退款并查询账单，使用真实 PostgreSQL 和 Lago；支付渠道在唯一外部适配器边界替换，并另做真实商户联调。以用户可见结果、余额、流水、订单和对账状态为断言，不断言私有函数结构或调用次数。
- 账本、订单/权益、支付适配器、周期计算、Lago 同步与对账在同一集成场景验证；模型执行复用既有 Bifrost 业务执行边界和受控供应商 HTTP 测试，不给每个内部模块另造测试框架。
- 既有先例包括组织作用域 API 合同、客户端幂等请求、LangGraph AG-UI/provider-boundary 测试、流式用量兼容测试；历史后端的 callback token、handoff、后台并发、Check-in、Goal/Routine 和 turn settle 测试作为恢复后端后的参考。
- 用真实数据库并发连接和可控时间测试：抢占同一余额、root Run 上限、多个积分批次、16 路重复结算/调整、同键不同内容冲突、数据库约束、提交前后进程退出、重启及待发送记录重放。
- 验证月末、闰年、跨年、原始日号恢复、提前续费、过期重购、跨周期已预留步骤、过期余量、退款冻结与到期竞争。来源批次和发生周期分别断言，不只检查最终总余额。
- 验证未知用量 24 小时释放、释放与结算同时发生、迟到成本平台承担、取消与断流、用户明确重试、暂停任务手动恢复和历史计划不补跑。
- 验证所有收费执行路径：主动对话、路由/标题等辅助模型、后台任务、Task、Delegation、Subagent、工具和计算资源。无预留、归属伪造、停用、越权、跨账户、供应商直连或内部自动重试不能绕过约束。
- 微信与支付宝分别覆盖真实付款、查单、关单、退款和账单核对；模拟通知重复/乱序/丢失、签名错误、金额不符、商户不符、两渠道成功、回跳未付、退款未知、订单关闭竞争及支付后故障恢复。
- Lago 实测复用非零用量零金额场景、重复 ID、并发重复发送、翻页间插入导致漏读/重复、整窗口重扫、微秒边界、迟到原周期调整。校验事件集合和内容，不仅比较汇总值。
- 正式适配器必须验证 occurrence_us 类型、范围及真实性；数据库保留精度不等于所有 API 返回精度一致。当前已测 PostgreSQL 社区版，不据此宣称 ClickHouse 或持续高负载通过。
- SQLite 参考模型已验证事务语义与行为样例，但不是生产后端。真实账本、进程故障、账户授权和执行覆盖尚需按相同外部行为重新验收；不得把模型通过标成生产功能完成。
- 三端收银台和账单在受支持浏览器/真机检查，确认回跳、登录归属、微小消费显示和异常状态。缺少商户联调、正式商品配置或完整后端时禁止真实销售。

## Out of Scope

- 自动扣款续费、免密协议、年付套餐、团队共享余额和跨个人账户积分转移。
- 周期中途按比例升降档、复杂折算、首期常规自助部分退款。
- 新增自带供应商密钥产品支持，或迁移现有 Claude/ChatGPT 订阅登录路径。
- 重做 Bifrost 模型网关、Casdoor 身份或 Corsair 连接器规格；仅与其可信身份、付款归属及执行边界集成。
- 依赖 Lago Premium 时区、非开票配置或通用手工收款能力，修改许可检查，或让 Lago 再次扣减积分。
- 用浏览器余额校验、部署 token、事后遥测或网关预算代替服务端逐步积分预留。
- 把历史后端直接恢复到生产、重写整个后端以默认为依赖已解决，或把参考模型当作生产账本。
- 开通未经验证的全部支付浏览器场景、全部模型/Harness/工具组合、无成本上限收费资源。
- 本规格不规定正式售价、资源单价或运营额度；这些是上线前必须完成的配置，不由演示数字推导。
