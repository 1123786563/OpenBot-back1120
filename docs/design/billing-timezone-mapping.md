# 北京时间周期与 Lago UTC 对账

## 已确认的边界

OpenBot 使用 Asia/Shanghai 管理用户周期、权益和积分批次。Lago 社区版保留 UTC，持续计量关系不随用户套餐周期切换；不购买许可或修改许可检查来设置时区。Lago 原始账单仅是 UTC 核算视图，不驱动用户续费、到期或扣分。

## 周期计算

保存首次实际开通的本地日期、时间及原始日号。每次从原始锚点计算目标月份，日号取原始日号与当月最大日号的较小值，不能从上次截短日期继续加一个月。过期后重新购买建立新锚点。

周期统一表示为 `[start_at, end_at)`；在 Asia/Shanghai 算出两个边界后分别转换为 UTC 瞬时保存。恰好在结束时间发生的事件归下周期，不通过减一秒或减一微秒改变边界。

| 原始锚点（北京时间） | 下一边界 | 再下一边界 |
| --- | --- | --- |
| 2024-01-31 00:00 | 2024-02-29 00:00 | 2024-03-31 00:00 |
| 2025-01-31 00:00 | 2025-02-28 00:00 | 2025-03-31 00:00 |
| 2024-08-31 09:30 | 2024-09-30 09:30 | 2024-10-31 09:30 |

例如第一行的首周期为 UTC `[2024-01-30 16:00, 2024-02-28 16:00)`。不能直接拿一个 UTC 月度账单总数与它比较，也不能按小时比例拆分账单总数；必须按事件归集。

## 对账算法

1. 本地原始记录保存稳定事件 ID、计量关系 ID、步骤 ID、原始发生时间、用量或整数微积分、费用承担方及接收时间。原始时间使用整数微秒，并作为 `properties.occurrence_us` 上报；API timestamp 从同一整数生成十进制秒字符串，不能通过浮点数转换。发送和重试始终使用原始时间，不改成补传时间。
2. 对目标北京时间周期转换得到的 UTC 窗口，查询 Lago 原始事件，限定计量关系与指标，读取全部分页。查询窗口向两端各扩一秒以作粗筛，最终按经本地原记录校验的整数 occurrence_us 严格过滤 `start_us <= occurrence_us < end_us`。Lago 时间过滤包含两个端点，且 GET/list 的 timestamp 序列化仅保留毫秒，不能用它判断微秒级周期归属。缺失或与原记录不符的 occurrence_us 进入差异清单，不以截断的 timestamp 静默代替。
3. 按计量关系、指标和事件 ID 核对两边的事件集合与内容，再按资源单位、费用承担方分别汇总。资源用量不能与微积分相加。缺失事件、同 ID 内容冲突、重复本地记录都进入差异清单。
4. 分页并非数据库快照：补传可能使事件跨页移动。扫描结果按稳定 ID 去重，对仍有补传的窗口重扫；对缺失 ID 单独回查并与本地发送记录核对。分页读取一次或两次总额相等都不能证明对账已完结。
5. 已关闭窗口的迟到事件仍可触发重新对账。本地同步回执和接收时间推动受影响周期重算，不只扫描当天发生的事件。记录扫描范围、截止接收时间、缺失集合和未完成补传项，不将暂时差异标成用户欠款。

每次对账固定一个本地已持久化发送序号水位 K，并记录截至 K 的预期事件 ID、内容摘要和同步状态。重扫应核对该集合而不是等待两次总数相同；未确认发送的记录保持 pending，扫描期间超过 K 的新记录留待后续轮次。即使集合完整，也只表示截至该水位已对齐，不表示历史周期以后不会再出现迟到事件。所有事件 ID 在所属计量关系内保持唯一，同 ID 内容改变必须拒绝并报警。

occurrence_us 是 OpenBot 写入的核算依据，Lago 不验证其真实性。适配器必须检查整数类型、支持的时间范围、与本地原记录及提交 timestamp 的一致性；不能接受客户端随意指定周期时间。数据库及跨语言传输禁止隐式浮点转换，超出消费者精确整数范围必须拒绝或采用明确约定的十进制字符串协议后重新验收。

UTC 账单核对沿用 Lago 实际返回的 UTC 边界，形成另一份汇总。北京时间用户周期与 UTC 核算周期都来自同一事件集合，周期之间通过事件 ID 关联，不要求两份月度总数一一相等。

## 跨周期步骤与积分来源

消费发生时间、结算完成时间和被扣积分的来源周期是不同维度。跨周期步骤完成后，使用原预留批次结算，批次所属周期不能从 Lago 事件时间反推。一个步骤使用多个批次时保留各批次扣减明细，并与步骤总扣分校验；已过期批次的预留余量直接过期。

对账分别核对发生时间视图与来源批次视图。记录在边界之后结算、但使用旧周期积分，并不构成差异。长时资源的实际计量时间规则由资源适配器明确；本映射不将所有用量强制归到结算时刻，也不改写原发生时间以迁就旧批次。

## 迟到事件与原周期调整

已出账窗口不覆盖历史快照。追加调整记录，引用原周期、原事件及本次差异，展示“原快照 + 已确认调整”；调整幂等键必须包含原事件与调整类型，重复补传不能重复增加调整。

调整唯一键以计费账户、原事件、调整类型为作用域；原周期与金额是不可变内容，不能把金额放进唯一键使重复请求变成新记录。同键同内容重试返回既有结果，同键不同周期或金额报冲突。合法的后续更正必须是另一个有来源的追加事件，而不是覆盖旧调整。调整记录与待同步记录在同一事务提交。

Lago 不自动重算既有账单时，由 OpenBot 保留追加调整作为对账依据；不为让旧账单数值吻合而重新扣用户积分或重复发送相同消费。超过 24 小时释放预留后才确认的成本按既定规则归平台承担。

## 验证范围

日历与跨周期来源批次的可执行设计样例见 [验证脚本](../../scripts/verify-billing-periods.py) 及 [结果](evidence/billing-periods/summary.json)。这不是生产账本实现。真实 Lago API 验证结果在验收清单中另列，不能以本地样例代替生产并发、补传和账本集成验收。

真实 API 结果见 [运行摘要](evidence/lago-timezone/summary.json)：北京时间两个相邻周期分别为 5、23 微积分，迟到补传后变为 22、23，重复补传不增加。UTC 二月账单 15 与原始事件 32 的差额为追加调整 17，验证了按事件重建不同时间窗口的必要性。测试为整秒、静态分页；生产重扫与亚秒时间保真仍待验收。

后续 [并发与精度实测](evidence/lago-concurrency/summary.json) 已复现分页插入引起漏读与重复，并验证重扫去重恢复预期集合；8 个并发请求仅保存 4 个唯一事件。数据库和时间过滤保留微秒，API 响应截断到毫秒；整数 occurrence_us 的粗筛后精确过滤通过 1 微秒窗口测试。以上限于 PostgreSQL 社区版，不是持续负载测试或生产适配器验收。

[事务账本参考模型](../../scripts/verify-billing-ledger.py) 验证跨周期多批次结算、并发重复结算、调整唯一约束、崩溃前回滚和超时释放；[结果](evidence/billing-ledger/summary.json) 与真实 API 验收分开记录。该模型使用临时 SQLite 数据库，不是 OpenBot 后端实现，不证明生产数据库的隔离级别或运行拦截点已经正确。
