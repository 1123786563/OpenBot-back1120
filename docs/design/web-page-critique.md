# 为 OpenBot Web 页面评分

使用 Impeccable `critique` 评估用户能否完成页面的主要任务。每轮评审一个页面或一个有明确起止点的流程。涉及多个页面时，分别记录分数和阻塞项。

## 1. 确定页面和任务

从仓库根目录启动本地环境。启动命令和端口见[开发指南](../development.md)。在测试账号或个人版测试环境中准备可重复使用的数据。从 `app/` 发起评审。产品约束见 [PRODUCT.md](../../app/PRODUCT.md)。以实际渲染的页面为准，记录源码路径和运行 URL。

第一轮可以从 Bots 列表和创建流程建立基线。这是 [Astryx 迁移试点](astryx-migration.md)。

| 页面 | 评审任务 | 验证完成的条件 |
| --- | --- | --- |
| `/bots` | 找到已有 Bot，或创建一个 Bot | Bot 出现在列表中，重新打开后仍可找到 |
| `/channel/new` | 选择 Bot 并发出第一条消息 | 进入新对话，消息出现在记录中 |
| `/channel/:id` | 查看 Bot 的进度并回复待处理事项 | 能辨别当前状态，处理结果出现在对应对话中 |
| `/connections` | 查看一个 App 的连接状态和下一步操作 | 能区分已连接、未连接和失败状态 |
| `/settings` | 切换界面语言 | 标签立即更新，对话内容保持原样 |

记录页面模式、用户角色、主要任务、成功条件、版本（团队版或个人版）、提交 SHA、工作区是否有未提交改动、实际主题和皮肤。表中页面以完成任务为主，使用 `Operate` 模式。如果要比较旧界面和 Astryx，为两种实现分别留档，使用相同的任务和数据。

## 2. 采集证据并运行评审

以 Bots 列表为例，从 `app/` 在 Codex 中使用以下提示词。其他页面替换路径、角色和任务。命令用法见 [Impeccable 官方文档](https://impeccable.style/docs/critique/)。

```text
$impeccable critique src/routes/_authed/_app/bots.index.tsx
从当前 app/ 目录加载产品上下文。运行页面为 http://localhost:3010/bots。
以有权创建 Bot 的团队版用户为主，评审找到已有 Bot、创建 Bot、刷新后找到新 Bot 的流程。
按照 ../docs/design/web-page-critique.md 取证并输出评分表、优先问题和复评条件。
```

1. 用桌面 `1440×900` 和窄屏 `390×844` 走主任务。先核对默认主题，再检查深色主题和另一种界面语言。涉及版本差异或 Astryx 回退时，补查受影响的版本和实际可见的界面变体。只对报告中列出的组合下结论。
2. 覆盖正常、加载、空白、错误及恢复状态中与任务有关的部分。用键盘走一遍主任务，检查焦点可见性、顺序和弹窗的焦点回退。为问题保留截图、复现步骤和所见结果。截图使用测试数据。
3. 按 `critique` 的流程独立完成 A（走查并评分）和 B（源码检测及浏览器证据）。汇总时采用 A 的分数。逐条复核 B 的发现，把确认的问题与相应操作和界面状态关联起来。若技能允许回退到单上下文，先完成 A，再查看 B，并按技能要求标注降级原因。
4. 遇到登录跳转、测试数据不足或无法触发的状态时，记录实际到达的页面和原因。把依赖这些证据的评分项标为 `未验证`。如果其余状态已足以支持某项评分，仍可给分并写明覆盖范围。

## 3. 记分并确定优先级

Impeccable 的十项启发式各评 `0–4` 分。结合实际表现使用各项的详细评分标准。一般来说，`0` 表示完全缺失或不可用，`1` 表示严重不足，`2` 表示部分可用且有明显缺口，`3` 表示主任务顺畅但有小问题，`4` 表示相关状态都表现出色。

| # | 启发式 | OpenBot 走查重点 |
| --- | --- | --- |
| 1 | 系统状态可见 | 用户能看到保存、发送或 Bot 执行进度吗？ |
| 2 | 符合用户理解 | Bot、Computer、App 和 Connection 的含义清楚吗？ |
| 3 | 用户控制与退出 | 用户能取消、返回或停止操作，并知道当前内容是否保留吗？ |
| 4 | 一致性与约定 | 相同操作的名称、位置和行为是否一致？ |
| 5 | 预防错误 | 页面能在提交前指出缺失值，防止误操作吗？ |
| 6 | 识别优于记忆 | 用户能看到当前 Bot、连接及可用操作吗？ |
| 7 | 灵活性与效率 | 用户能高效查找、切换或重复完成常用任务吗？ |
| 8 | 视觉层级与简洁 | 主操作、进度和待处理事项好找吗？ |
| 9 | 错误诊断与恢复 | 失败后用户知道原因、下一步和如何重试吗？ |
| 10 | 帮助与文档 | 用户能在需要时找到完成任务的指引吗？ |

每项写一句依据。确实不适用的项标 `N/A` 并解释原因。适用项全部有评分时，满分为 `4 × 适用项数`，例如 `24/32 = 75%`。按比例定档。`≥90%` 优秀，`≥70%` 良好，`≥50%` 尚可，`≥30%` 较差，其余为严重。存在 `未验证` 项时，报告已评分项与待验证项，总分和档位暂缺。

按用户影响给问题定级。`P0` 表示主任务完全阻塞，`P1` 表示遇到明显困难或容易误操作，`P2` 表示有可行办法绕过的轻度干扰，`P3` 表示不影响任务完成的细节。先处理 P0 和 P1，即使总分落在良好或优秀档。

## 4. 留档并复评

把完整评分表、问题和证据交付给本轮评审人。在评分完整且允许保存报告时，`critique` 会把快照保存到 `app/.impeccable/critique/`。评分暂缺时，在评审记录保留证据和待验证项。团队需要共享时，将脱敏后的报告放入现有评审记录。仓库默认忽略 `.impeccable/`。

用下面的模板记录一轮评审。将方括号中的文字替换为本轮结果。

```markdown
# [页面或流程] 的 UX 评分

- 评审方法：[双代理，或降级及原因]
- 范围：[源码、实际 URL、任务、角色与成功条件]
- 基线：[提交 SHA、未提交改动、版本、主题、皮肤、语言、视口、测试数据]
- 覆盖：[已验证状态、未验证状态及原因]
- 评分：[逐项分数、理由、证据；总分、档位或暂缺原因]
- 优先问题：[级别、对应评分项、复现、所见结果、用户影响、修复建议、复评通过条件]
- 可保留的表现：[操作、效果与证据]
- 复评：[相同场景的前后分数、已关闭问题、仍待验证的问题]
```

修复后用相同任务、角色、数据、视口和评分项复跑。逐条核验复评条件。若覆盖或适用项变化，分别列出两轮分数和满分，并说明变化。为能够稳定复现的关键交互补写行为断言。实践见 [Web 浏览器端到端测试 ADR](../adr/0009-web-browser-e2e.md)和[现有测试说明](../../tests/e2e/README.md)。
