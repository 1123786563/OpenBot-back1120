# OpenBot 管理实时积分与支付，Lago 汇总用量并核算账单

首期优先使用自托管 Lago 社区版。OpenBot 是可消费积分的唯一权威，负责积分发放、到期、预留、按步骤结算、退款冻结及运行消费上限，并直接对接自有微信支付和支付宝商户号。Lago 负责用量汇总与账单核算，不再次扣减用户积分。

该边界用于统一处理并发预留、跨周期结算、未知用量释放及退款规则，避免两套可写余额互相覆盖；代价是 OpenBot 必须维护完整、可追溯的积分账本和同步机制。优先通过公开接口集成，不修改 Lago 支付内核或绕过商业许可检查；确需商业功能时另行讨论采购。

每日核对渠道交易、本地订单、积分流水与用量核算。差异先调查，不自动覆盖余额或追扣用户；核实的漏发权益可幂等补发，金额不符、重复收款与退款异常转人工处理。调整追加流水并保留原因，不修改历史记录。

本 ADR 确认职责边界，接口能力仍需运行验证。完整产品规则见 [计费设计](../design/billing.md)。

后续确认：本地账本及用量记录可靠时，Lago 故障不阻断消费，恢复后补传；本地无法可靠保存记录则停止新增收费步骤。积分消耗与人民币收款分开核对，不将积分消耗作为新的人民币应收。每个消费账户建立持续计量关系，与月付套餐权益分离；用户账单以 OpenBot 支付、退款及积分记录为准，Lago 原始账单首期仅供运营核算。

首期采用零金额用量核算候选方案，不要求 Lago 独立复算逐步积分价格。资源用量和整数微积分分别上报，通过步骤 ID 关联；只同步核算必需信息。迟到用量保留原时间形成原周期调整，平台承担与用户承担分开汇总。零金额路径必须通过运行验证后才能用于生产。

时区边界已明确：保留社区版 Lago 的 UTC 核算，OpenBot 按 Asia/Shanghai 和原始购买日锚点管理周期。按原始事件时间映射并逐事件对账，不直接比较两套系统的月度账单总数；迟到事件形成原周期追加调整。此选择保持原有北京时间产品规则，代价是 OpenBot 需要维护周期归集和调整记录。具体映射见 [时区设计](../design/billing-timezone-mapping.md)。

运行证据进一步约束适配器：Lago 响应时间仅保留毫秒，因此以 OpenBot 的原始整数微秒记录及回传的 occurrence_us 核对精确周期归属。分页扫描依据本地持久化事件集合与水位重扫，不把 Lago 的分页当作快照。调整和结算以唯一业务身份、不可变内容及事务内待同步记录保证可重试；已完成的 SQLite 模型验证不替代生产后端验收。
